DATA SHARING · AUTHORIZED EDITING · AUDITING

LGPD Chain

An interface for registering, sharing, retrieving, and verifying user information on an editable blockchain.

This application is part of a master's research prototype on editable blockchains. It brings data blockchain operations together in a web interface: from preparing and publishing a record to correcting information, exercising the right to be forgotten, and issuing a certificate.

Sharing information while retaining control over changes

Imagine a consortium of companies accessing customer information on the same private blockchain. Participants need consistent data, but they may not fully trust one another or the infrastructure administrator. At the same time, customers need to correct information and request its removal.

In a conventional blockchain, modifying recorded data can invalidate the chain's cryptographic links. The approach accessed through this app combines chameleon hashing, which enables authorized changes, with integrity checks and a Cuckoo Filter, which support the auditing of records and erasure operations.

In this usage model, each data subject controls the private key associated with their data. Authorized participants can access and verify the shared information; producing a change that preserves the original cryptographic commitment requires the corresponding private key.

What this protection means: unauthorized changes can be detected through cryptographic verification. Protection depends on the security of the keys and infrastructure. It does not prevent someone from copying information they have already accessed, nor does it establish whether information was truthful when first registered.

From registration to verification

  1. PrepareCreate the local record and obtain the chameleon hash parameters.
  2. PublishCompute the data hash and submit the record to the blockchain.
  3. ManageInspect blocks and authorize corrections or erasure using the trapdoor.
  4. VerifyCheck integrity and retrieve the recorded evidence of deletion.

Three components with different roles

  • Web interface: organizes records, operations, results, and certificates. It supports English and Portuguese, as well as light and dark themes.
  • Local SQLite database: the server/front.sqlite file stores local users, settings, API access logs, and the certificate template.
  • Blockchain: a service accessed through REST APIs maintains the blocks, associated data, and cryptographic mechanisms. Saving a user locally does not automatically publish that user on the blockchain.

What is the trapdoor?

The CH Trap Door is the chameleon hash private key. It allows new parameters to be computed for a modified message while preserving the original hash. The public key allows this relationship to be verified, but it cannot replace the trapdoor when authorizing changes.

In this prototype, key generation and collision generation functions are accessed through APIs. The trapdoor entered in the modal is sent to the computation service, which therefore forms part of the demonstration's trusted environment. Hiding a key with the eye icon protects its on-screen visibility; it does not encrypt the stored key.

Users · Preparing and managing user records

The Users / Blockchain users screen brings together local records. Each record contains a name, identifier, address, telephone numbers, email addresses, and chameleon hash keys.

  • Manual creation: opens a record with empty fields to be completed and saved.
  • Automatic creation: generates the requested number of fictional users, updating the list and counter as each record is created.
  • Create: the buttons beside individual fields generate sample data; names and addresses use the available country profiles.
  • Get from blockchain: requests chameleon hash key generation using the bit length configured in Settings.
  • Save user and Delete user: save changes or remove local records after confirmation. Local deletion does not exercise the right to be forgotten on the blockchain.
  • Multiple selection: lets you select records using Ctrl and Shift and delete them sequentially after confirmation.

Sending data to the blockchain

The Send to blockchain button opens a modal containing the data prepared for publication. The private key is displayed separately, hidden by default, and is not included in the record's public content. First, Sign infodata computes the chameleon hash. A valid signature enables submission. When the blockchain confirms creation, the local record is marked as Sent to blockchain.

The totals of sent and unsent users help track progress. The Not Sent filter displays records whose local sent state is false; the Sent filter displays those marked as sent. This state represents the local submission history, not a fresh blockchain integrity check.

To submit several pending records, use Send not sent to blockchain: enter the quantity and the interval between submissions. The app signs and sends each eligible user, updates the counters, and displays the wait until the next submission. Canceling stops the sequence; records already confirmed remain sent.

Check user on blockchain queries the Cuckoo Filter. A membership query alone does not replace right-to-be-forgotten verification using the identifier and certificate: absence may also indicate a user who was never registered.

Blocks · Inspecting the blockchain

The list loads the number of blocks defined in Settings, displays the most recent first, and periodically checks for new blocks. The Reload button allows a fresh manual query. Filters help locate items by number, data address, and date range.

Each block shows its number and date and time. Expanding it prompts the app to retrieve its full details and organize them into three tabs:

Correcting data

Under User Data, the Edit button opens the editing modal. Enter the new infodata content and the trapdoor. Once the signature is validated, submit the change to the blockchain. After confirmation, the app retrieves the block again to display the updated information.

Right to be Forgotten · Requesting erasure

This workflow requests the replacement of personal data associated with the record with a deletion message. It uses the trapdoor to generate the parameters required for the authorized change.

  1. Open the desired block and select User Data → Right to be Forgotten.
  2. In the confirmation modal, enter the CH Trap Door corresponding to the record.
  3. Click Confirm. The app requests a collision for the message containing deleted: true and the reason for erasure.
  4. If the API confirms a valid signature, click Send to Blockchain. The request is submitted in deletion mode.
  5. Monitor the result. When the operation is confirmed, the app reloads the block data.

Evidence of deletion can later be retrieved through the certificate and blockchain verification functions. Removal from the service does not automatically delete previously exported copies, local records, or histories maintained by other participants.

Data verification · Checking results

Block Verifier

Enter the block number and click Verify block. The service checks whether the computed hashes match the block's references. The result appears in green for validity or red for failure. The button remains disabled while the query is in progress.

Issue a certificate

In the block details area, next to the JSON tab, the Issue a certificate button becomes available when infodata.deleted indicates deletion. Enter the user's original identifier: the app computes its SHA3-256 hash and compares it with userdata_id_hash in the metadata.

If the values match, a PDF is generated using the template saved in Settings, containing the entered identifier, the cuckoofilter_hash, and the block's date, time, and number. The modal allows you to preview and download the document, with selectable text over the background image.

Verify right to be forgotten

On the verification screen, enter the original User ID Number and the Right to be forgotten certificate, whose value is the corresponding cuckoofilter_hash. Click Verify in blockchain. The response reports the result in the selected language; on success, it also displays the block number and time_stamp.

The PDF organizes the information for reference and sharing. Verification against the blockchain is what allows the references presented in the document to be checked.

Transactions · Request history

This screen associates each logged request with its response: method, route, date, time, and JSON content. Expanding an item allows you to examine what was sent and what was returned. Filters by route, date range, and order help investigate errors and track operations.

Routes included in the Settings exception list are not recorded in this local history. This allows frequent internal queries to be excluded. Logs are operational records of the application and may contain data sent to the APIs; they complement cryptographic auditing but do not replace it.

Settings · Configuring the environment

  • Local database: displays the SQLite file used by the app.
  • Blockchain APIs: configures the address, port, query routes, and number of blocks to load.
  • Chameleon hash: defines the bit length used in key generation requests.
  • History exceptions: determines which internal routes will not be logged in Transactions.
  • Interface: selects the language and theme and allows the presentation HTML to be edited in English and Portuguese.
  • Certificate: uploads the JPG background and adjusts the position, font, size, and color of the certificate's four text fields, with a real-time preview.

Use Save settings to persist changes. To get started, check the blockchain connection, create a test record, publish it, and inspect its block. Then explore editing, verification, and certificate issuance using fictional data.

LGPD Chain · An academic prototype for accessing an editable blockchain. The application provides technical mechanisms for modification and verification; participants remain responsible for managing shared information and keys.
